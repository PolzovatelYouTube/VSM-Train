# Авторитетный пересчёт попытки

`POST /api/attempts` принимает только идентификатор игрока, режим, идентификатор
сценария и упорядоченный журнал действий:

```json
{
  "playerName": "Ирина Петрова",
  "scenarioId": 12,
  "mode": "check",
  "actions": [
    { "type": "choice", "nodeId": "medical-start", "choiceId": "call-medic", "timestampMs": 45120 }
  ]
}
```

Клиент не отправляет `score`, `loyalty`, `safety`, компетенции, XP или итоговый
журнал. Сервер загружает сохранённый сценарий, прогоняет `actions` через тот же
чистый `shared/engine.ts` и только затем сохраняет рассчитанные шкалы, результат
и журнал в SQLite.

Replay отклоняет действия вне длительности сценария, действия не по порядку,
ответ вне активного узла и вариант, скрытый условием сценария. Ручной запуск
разрешён только для событий с триггером `manual`. Если в режиме `check` ответ
не поступает до дедлайна, таймаут применяет сам сервер.

`timestampMs` — виртуальное время симуляции от начала рейса. Для production
версии следующим шагом следует создать серверную сессию рейса и подписывать
действия её идентификатором: это позволит измерять реальное wall-clock время
реакции без доверия к часам браузера.

## Одновременные ситуации

`gameplay: "concurrent"` (значение по умолчанию) включает независимые сроки
ситуаций в обоих режимах. `sequential` явно сохраняет прежнюю очередь и паузу
диалога в тренировке. Старый формат `version: 1` продолжает загружаться.

Журнал включает фокус и информационные переходы:

```json
[
  { "type": "select", "eventId": "breathing", "timestampMs": 24000 },
  { "type": "choice", "eventId": "breathing", "nodeId": "breathing-start", "choiceId": "medical-radio", "timestampMs": 24000 },
  { "type": "select", "eventId": "socket", "timestampMs": 25000 },
  { "type": "choice", "eventId": "socket", "nodeId": "socket-start", "choiceId": "socket-delegate", "timestampMs": 25000 },
  { "type": "continue", "eventId": "socket", "nodeId": "socket-result", "timestampMs": 29000 }
]
```

`select` допустим только для появившейся открытой ситуации; `leave` оставляет
текущую ситуацию ждать (`timestampMs`, без `eventId`). Переключение сохраняет
сроки. `continue` допустим только в текущем информационном узле и не добавляет
оцениваемый ответ. `choice` проверяет событие, узел и доступность варианта.
Старое действие без `eventId` допускает неявный фокус только при единственной
открытой ситуации.

`timeCostSec` продвигает общие часы: остальные события возникают и ухудшаются
во время работы. Клиент записывает timestamp **начала** действия; следующий
timestamp не может быть раньше завершения работы. Replay воспроизводит
стоимость, эскалации и фоновые таймауты тем же движком.

Пропущенное окно ответа, эскалации и нерешённые ситуации в конце рейса
фиксируются сервером с `cause`, пояснением и фактическими эффектами. Эскалация
срабатывает один раз. Последствия ожидания с `cause` не считаются неправильным
ответом: они влияют на шкалы и оценку управления нагрузкой. Таймаут решения
узла по-прежнему учитывается как пропущенное решение.

Сервер сохраняет `attempts.workload` — появление, выбор, уход, начало и завершение
действия, изменение признаков, эскалацию и исход. Записи включают время,
сохранённый узел/контекст, ожидавшие обращения и фактические эффекты.
Клиент присылает только действия; этот журнал вычисляется replay, а не принимается
из публичного запроса. Старая SQLite получает колонку с default `[]`.

`prioritization` и `situational_awareness` оценивают каждую стадию риска, включая
повторное ухудшение после первого ответа. Правила, веса, допустимые окна и пример
описаны в [механике одновременных ситуаций](multi-incident-gameplay.md).
