# ВСМ Тренажёр — песочница сценариев для проводников

Заготовка к хакатону «Геймифицированное обучение проводников ВСМ»: сервер, клиент и **2D-редактор сценариев** с видом на вагон сверху. В редакторе собирается состав, на карту ставятся пассажиры, каждому задаётся модель поведения (идти → сесть → сказать → запустить событие), а события описываются как граф диалога с таймером и эффектами на «лояльность» и «безопасность». Затем сценарий проходится в двух режимах: **тренировка** (пауза, подсказки, повтор) и **проверочный рейс** (без пауз и подсказок, фиксируется скорость реакции).

## Быстрый старт

```bash
npm install
npm run dev        # http://localhost:5000, горячая перезагрузка клиента
npm run check      # проверка типов
npm test           # тесты движка (vitest): условия, таймауты, ролевая модель, терпение, сценарий «Ситуации на борту»
npm run build      # сборка в dist/
npm start          # продакшен-сервер из dist/
```

База данных — SQLite-файл `data.db` в корне (создаётся автоматически; при запуске добавляются встроенные сценарии, если их ещё нет: демо, «Ситуации на борту» из `shared/scenarios/onboard.ts` и «Маломобильные пассажиры и бесхозная вещь» из `shared/scenarios/accessibility.ts`). Ничего ставить отдельно не нужно.

Демо-данные (`server/seed.ts`) — **синтетические**: 2 депо × 2 бригады × 5 вымышленных проводников, 2 челленджа и история рейсов за 20 дней. История получена прогоном бота по тем же сценариям тем же движком (детерминированный ГСЧ), поэтому рейтинг, сгорающие баллы и страница руководителя сразу не пустые. Чтобы начать с чистого листа — удалите `data.db`.

### Что изменилось

- **Два режима на главной.** Карточки «Начать смену» (выбор сценария → «Тренировка» / «Проверка») и «Создать сценарий» (редактор, предпросмотр, удаление, новый сценарий). Выбор запоминается в `localStorage`.
- **Игровая сцена вместо карты сверху.** Рейс показывается как вид сбоку на салон: интерьер вагона, окна с параллаксом пейзажа (день/закат/ночь), персонажи-спрайты с состояниями `idle/walk/sit/talk/listen/positive/negative` и эмоциями. Камера переходит к участнику события и делает наезд в диалоге.
- **Последствия выбора видны.** После ответа или таймаута на ~1,3 с показывается реакция: отметка над персонажем, смена эмоции, вспышка по краю кадра, плашка с изменением шкал и разбором (`option.feedback` / `onTimeout.text`), всплывающие дельты у шкал HUD. Пока идёт реакция, симуляция стоит, а время реакции на следующий узел отсчитывается заново — оценка не меняется (см. тест `tests/visual.test.ts`).
- **Диалог:** клавиши 1–4, Tab/Enter, touch; реплика в `aria-live`; в проверке — полоса-таймер и текст «Осталось N с / Срочно»; повторный выбор во время реакции заблокирован.
- **Мини-карта** (прежний `CarMap`) стала вспомогательной: сворачивается, на мобильном свёрнута по умолчанию.
- **Редактор:** вкладка «Сцена» — пейзаж, интерьер, пресет и цвет одежды персонажей, живой предпросмотр кадра и кнопка «Предпросмотр игры» (сохраняет и открывает тренировку).
- **Схема:** необязательные `ScenarioData.visual` и `Actor.visual`. Старые сценарии работают без миграции.
- Удаление сценария с главной страницы теперь требует подтверждения с названием сценария и предупреждением о необратимости действия.

### Формат сценария (упрощённо)

```ts
{
  train: { name, cars: [{ id, number, type: "first"|"business"|"comfort"|"standard"|"bistro", length, width, cells: Cell[] }] },
  actors: [{
    id, name, role: "passenger"|"vip"|"elderly"|"child"|"troublemaker"|"conductor",
    ticket: { carId, seat } | null,
    spawn: { carId, x, y }, mood: 0..100,
    steps: [ { type:"wait", seconds } | { type:"goto", target } | { type:"sit" }
           | { type:"say", text } | { type:"mood", delta } | { type:"emit", eventId } ]
  }],
  events: [{
    id, title, category, actorId,
    trigger: { type:"manual" } | { type:"time", atSec } | { type:"actor" } | { type:"condition", if: Condition },
    startNode, nodes: [{
      id, speaker, text, timerSec,
      onTimeout?: { next, effects, set?, text? },          // своя ветка, если не успел; иначе штраф TIMEOUT_PENALTY
      options: [{ id, text, next, effects:{loyalty,safety}, correct, hint,
        step?: "acknowledge"|"rule"|"solution"|"assure", // шаг ролевой модели
        set?: { flag: true|false|число },                 // выставляет флаги
        if?: Condition,                                   // вариант виден, только если условие истинно
        nextIf?: [{ if: Condition, next }] }]             // первый сработавший переход, иначе next
    }]
  }],
  durationSec, initial: { loyalty, safety }
}
```

`Condition` — `{ flag, eq? }` | `{ loyalty: { lt?, gte? } }` | `{ safety: { lt?, gte? } }` | `{ all: [...] }` | `{ any: [...] }`. Все новые поля необязательны: старые сценарии работают как раньше, тип вагона `second` при чтении превращается в `comfort`.

Компоновки вагонов: первый класс 2+1, бизнес и комфорт 2+2, стандарт 3+2. Терпение пассажира зависит от класса (`PATIENCE_BY_CLASS` в `shared/rules.ts`, ориентир — СТО РЖД 03.011 п. 10.5: 5 / 10 / 15 / 20 мин): в дорогих классах таймер короче, а потеря лояльности больше.

Цель шага `goto`: `ownSeat` (своё место по билету), `seat` (конкретное кресло), `cell` (координата), `zone` (туалет / бар / тамбур в указанном вагоне). Координаты: `x` — вдоль вагона, `y` — поперёк; проходимы клетки `aisle`, `seat`, `door`, `vestibule`, `toilet`, `bar`.

## Архитектура визуального режима

```
ScenarioData ─┐
              ├─ createSim / tick / chooseOption (shared/engine.ts — без изменений в логике)
SimState ─────┤
LogEntry ─────┘
      │
      ▼
projectGameScene(data, sim, { viewCarId, follow, consequence })   shared/visual.ts — чистая функция, Vitest
      │  → GameSceneModel { carId, phase, landscape, interior, focusedActorId, speakerId, characters[], consequence }
      ▼
play.tsx (Runner: rAF-цикл, визуальная пауза, предзагрузка)
  ├─ GameHud            время, режим, шкалы + дельты
  ├─ GameStage          камера и слои сцены
  │   ├─ WindowLandscape  небо + 2 слоя параллакса (CSS, memo — не рендерится на кадр)
  │   ├─ TrainInterior    стена, окна, полки, тамбуры, дальний ряд кресел, бистро
  │   ├─ CharacterSprite  спрайт по пресету; AssetFallback для неизвестного
  │   ├─ NearSeats        ближний ряд кресел (глубина)
  │   └─ ConsequenceOverlay
  ├─ DialogueStage      реплика, варианты, подсказки, таймер
  └─ MiniCarMap         TrainStrip + CarMap (compact)
```

Правила:

- `shared/engine.ts` не знает о визуале. Добавлен только `resetReactionClock()` — перезапуск отсчёта реакции после визуальной паузы.
- Проектор ничего не пишет в `SimState` и не считает очки. Всё визуальное (фаза, говорящий, состояние и эмоция персонажа, направление взгляда, глубина) выводится из данных движка.
- В `ScenarioData` хранятся только авторские настройки: `visual.landscape` (`day` | `sunset` | `night`, по умолчанию `day`), `visual.interior` (ключ реестра, по умолчанию по классу вагона), `actor.visual.preset` и `actor.visual.accent` (по умолчанию — по роли).
- Фоновые анимации (параллакс, покачивание, дыхание) — CSS `transform`/`opacity`. Скорость пейзажа не зависит от скорости симуляции. При `prefers-reduced-motion` анимации отключаются, остаются короткие crossfade.
- Раскладка (`.game-layout` в `index.css`): десктоп — сцена и боковая панель, диалог поверх нижней части сцены (камера поднимает кадр на высоту диалога); мобильный портрет — сцена ~45% высоты, диалог ниже; мобильный альбом — сцена слева, диалог справа.
- `editor` и `play` грузятся лениво (`React.lazy`); предпросмотр сцены в редакторе — отдельный ленивый чанк `ScenePreview`.

## История разработки

Первый коммит — стартовый прототип (собран с помощью ИИ-ассистента). Дальше команда ведёт работу небольшими итерациями: один коммит — одна задача, которую мы прочитали и можем объяснить.

## Стек

React 18 + TypeScript + Vite, Tailwind v3 + shadcn/ui, TanStack Query, wouter (hash-роутинг), Express 5, Drizzle ORM + better-sqlite3, Zod. Общий код `shared/` используется и клиентом, и сервером.

## Как расширять

- **Поменять правило начисления** (штраф, вес шкалы, порог ачивки) — одна константа в `shared/rules.ts`.
- **Новый тип шага поведения** — добавить вариант в `behaviorStepSchema` (`shared/scenario.ts`), обработать в `tick()` (`shared/engine.ts`, обработка шагов актора), добавить форму в `StepEditor` (`editor-panels.tsx`).
- **Новый тип клетки / вагона** — `CELL_KINDS`, `buildCar()` и отрисовка в `CarMap.tsx`.
- **Новая ачивка** — одна запись в справочнике `ACHIEVEMENTS` (`shared/achievements.ts`): правило описывается декларативно (`attempts`, `meter`, `reaction_below`, `accuracy`, `competency`, `challenges`).
- **Пороги навыков, XP, уровни, срок жизни баллов, частота уведомлений** — `SKILL_THRESHOLDS`, `CRITICAL_SKILLS`, `XP_RULES`, `LEVELS`, `POINTS_TTL_DAYS`, `NOTIFICATIONS_POLL_MS` в `shared/rules.ts`.
- **Новый челлендж** — строка в таблице `challenges` (правило — JSON по `challengeRuleSchema`); демо-челленджи — `server/seed.ts`.
- **Новый канал уведомлений** (push, e-mail, мессенджер) — функция-канал в массиве `CHANNELS` в `server/notifications.ts`; вызывающий код не меняется.
- **Новая метрика компетенций** — `computeResult()` в `shared/engine.ts`; лог `SimState.log` уже хранит каждое решение с временем реакции.

## Дорожная карта на хакатон

1. **XState** для движка событий — сейчас диалог это простой граф `nodes/options`; со стейт-машиной удобнее делать параллельные события и условия перехода.
2. **React Flow** — визуальный редактор графа диалога вместо списка узлов.
3. **PostgreSQL + Redis** — вместо SQLite; лидерборд на `ZINCRBY`/`ZREVRANGE`.
4. **WebSocket** — живой рейтинг и режим наставника (тренер наблюдает за рейсом в реальном времени).
5. **Авторизация** — сейчас игрок задаётся вводом имени в шапке.
6. **Контент** — реальные регламенты РЖД/ВСМ как базы для событий: медицинский инцидент, конфликт, безбилетник, задымление, эвакуация.

## Ограничения

- Визуальный режим — первая итерация: персонажи векторные и собраны из простых фигур, без покадровой анимации. Анимация ходьбы и реакций — CSS.
- Сцена показывает один вагон «вид сбоку»: оба ряда кресел по разные стороны прохода проецируются на глубину кадра. Точная рассадка и номера мест — только на мини-карте.
- Реплики «за кадром» (например, начальник поезда) помечаются «по рации»; отдельного спрайта у них нет. Говорящий сопоставляется с актором по имени в поле `speaker`.
- Пейзаж один на весь рейс (из `visual.landscape`); смена времени суток по ходу рейса не реализована.
- Контейнерные единицы `cqh` для параллакса требуют Chrome 105+ / Safari 16+ / Firefox 110+. В старых браузерах пейзаж стоит на месте.

- Подтверждение удаления использует нативный диалог браузера. Он доступен с клавиатуры и не требует новой UI-зависимости, но его оформление зависит от браузера и операционной системы.

## Принятые архитектурные решения

### Движок, сценарии и оценка

- **Data-driven сценарии.** Контент сценария — это валидируемая Zod-структура: поезд, персонажи, события, граф диалогов, условия и последствия. Редактор изменяет данные, а не логику `shared/engine.ts`; поэтому новый сценарий и ветка диалога не требуют переписывать ядро.
- **Детерминированный pure-TS движок.** Симуляция не зависит от React или Express: она принимает состояние и шаг времени, применяет триггеры, таймауты и эффекты. Одно ядро используется для интерфейса, тестов и серверной проверки результата.
- **Две независимые шкалы.** Лояльность пассажира и безопасность меняются каждым решением раздельно и входят в итоговую оценку вместе с точностью и таймаутами. Числовые правила и пороги собраны в `shared/rules.ts`.
- **Методическая ролевая модель.** Вариант ответа может быть помечен шагом «признать ситуацию → обозначить правило → предложить решение → заверить». Движок фиксирует нарушения порядка и учитывает их в обратной связи и компетенции.

### Авторитетный пересчёт попытки

Клиент не передаёт результат рейса: ни баллы, ни шкалы, ни XP, ни компетенции. В `POST /api/attempts` отправляется только упорядоченный журнал входных действий:

```json
{
  "playerName": "Ирина Петрова",
  "scenarioId": 12,
  "mode": "check",
  "actions": [
    { "type": "choice", "nodeId": "medical-start", "choiceId": "call-medic", "timestampMs": 45120 }
  ]
}
```

Сервер загружает сохранённую версию сценария, воспроизводит журнал через `shared/replay.ts` и только затем сохраняет рассчитанные лог, шкалы, компетенции и итоговый балл. Replay отклоняет действия вне времени сценария, не по порядку, не в активном узле или недоступные по условию. Ручной запуск разрешён только для sandbox-событий с триггером `manual`; сервер также самостоятельно применяет таймауты проверочного режима.

Это защищает рейтинг и достижения от прямой подмены результата в браузере. `timestampMs` пока является виртуальным временем от клиента, поэтому для production-версии следующим шагом должна стать серверная сессия рейса с серверными часами: это исключит подмену времени реакции.

### Неизменяемая выдача достижений

Достижение фиксируется один раз в таблице `achievement_awards`: игрок, идентификатор достижения, время выдачи и попытка-источник. После каждой сохранённой попытки правила достижений по-прежнему проверяются декларативно, но в таблицу добавляются только новые награды. Профиль читает факт выдачи из этой таблицы и не отменяет ачивку при последующих изменениях правил, истории или компетенций. Для существующей базы выполняется одноразовое восстановление: награда привязывается к первой исторической попытке, на которой правило стало выполнено.

### Уведомления: осознанный polling

Для новых сценариев, челленджей и напоминаний о сгорающих баллах выбрали polling раз в 20 секунд (`NOTIFICATIONS_POLL_MS`), а не WebSocket: секундная задержка для этих событий не критична, зато решение не требует постоянного соединения и отдельной stateful-инфраструктуры. Запрос и кэш находятся в `client/src/lib/api.ts`; `NotificationBell` не вызывает `fetch` напрямую.

Серверная синхронизация идемпотентна для уведомлений, которые создаются во время опроса: о каждом активном челлендже запись появляется один раз, а напоминание о сгорающих баллах — не чаще одного раза в 24 часа. Это проверяется в `tests/notifications.test.ts` многократными вызовами синхронизации.

Если впоследствии понадобится меньшая задержка именно для server-to-client уведомлений, подходящим следующим шагом будет SSE. SSE в текущем коде не реализован и специальной абстракции для него нет. WebSocket остаётся вариантом для будущих двусторонних сценариев, например режима наставника или живого взаимодействия во время рейса.

### Учётные записи и роли

Вместо выбора имени в шапке пользователь создаёт учётную запись и входит по паролю. Пароль хранится только как bcrypt-хеш; API выдаёт JWT сроком на 8 часов, который клиент передаёт в заголовке `Authorization: Bearer`. У роли `conductor` есть доступ только к собственному профилю, попыткам, челленджам и уведомлениям. Роль `supervisor` дополнительно управляет сценариями и получает доступ к аналитике бригады. Публичная регистрация всегда выдаёт роль проводника: руководитель назначается администратором в БД или будущей HR-интеграцией. В production обязательно задаётся переменная окружения `JWT_SECRET`; без неё сервер не запускается.

Этот блок описывает реализованную замену демонстрационного выбора имени; более ранняя оговорка об отсутствии авторизации относится к исходному прототипу.

После внедрения учётных записей `playerName` из более раннего примера запроса больше не принимается: `POST /api/attempts` получает только сценарий, режим и журнал действий, а имя игрока сервер берёт из проверенного JWT.

Для локального создания первого руководителя используется отдельная администраторская команда, недоступная через HTTP:

```bash
npm run auth:create-supervisor -- "Имя руководителя" "пароль-не-короче-8-символов"
```

### Границы MVP

- Уведомления реализованы как in-app канал с периодическим опросом; push, e-mail и мессенджеры оставлены расширением канала доставки.
- SQLite выбран для локального запуска и демонстрации. Для высокой нагрузки рейтинг может быть вынесен в PostgreSQL и Redis, но текущая реализация не требует дополнительной инфраструктуры.
- Профиль создаётся по имени и предназначен для демо. Корпоративная авторизация, роли и синхронизация с HR/LMS — следующий интеграционный этап.
